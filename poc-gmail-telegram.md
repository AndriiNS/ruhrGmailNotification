# PoC: Gmail → Telegram

Статус: **теоретичний аналіз за документацією (25.10.2026). Нічого не протестовано.**
Позначки: ✅ підтверджено документацією, ⚠️ потрібно перевірити тестом або запитом до джерела.

## 1. Потік

1. Користувач входить через Google OAuth (`access_type=offline`), ми зберігаємо refresh token (зашифровано).
2. Бекенд викликає `users.watch` для скриньки; Gmail публікує події в Cloud Pub/Sub топік.
3. Подія містить лише `emailAddress` і `historyId`. Бекенд викликає `users.history.list` з попереднім `historyId`, отримує ID нових листів.
4. Для кожного нового листа читаємо метадані (відправник, тема) і надсилаємо `sendMessage` у Telegram.
5. Зберігаємо `historyId` і ID оброблених листів (дедуплікація).

## 2. Gmail: дозволи і верифікація

- ✅ `gmail.metadata` (заголовки й мітки, без тіла листа) і `gmail.readonly` — **restricted scopes**. Для них потрібна restricted-верифікація і щорічна безпекова оцінка (CASA).
- ✅ Гірше, ніж «sensitive»: sensitive-рівень вимагає лише перевірки бренду, restricted — ще й аудит.
- ✅ Мінімальний варіант для нашої задачі — `gmail.metadata`: він відповідає принципу «не зберігати тіло листа» з плану. ⚠️ Перевірити тестом, що `history.list` і `messages.get(format=metadata)` працюють лише з цим scope (відомі обмеження metadata-scope, напр. щодо параметра `q`).
- ✅ Доки застосунок у статусі **Testing**: до 100 тестових користувачів, а авторизація (разом із refresh token) спливає через 7 днів. Для PoC на власному акаунті цього достатньо, для публічного запуску — ні.
- Вартість CASA: ⚠️ за публічними прайсами сторонніх асесорів Tier 2 коштує приблизно $540–720 на рік за застосунок. Це не офіційна ціна Google, перед бюджетуванням уточнити в асесора. Вища категорія (Tier 3) значно дорожча.

## 3. Gmail: виявлення нових листів

- ✅ Push: `users.watch` + Pub/Sub. Watch треба поновлювати **щонайменше раз на 7 днів**, інакше сповіщення тихо припиняються; практична рекомендація — поновлювати щодня.
- ✅ Резерв: періодичний `history.list`, якщо давно не було подій. Потрібен як страховка від пропусків.
- ✅ Налаштування GCP: топік, права публікації для `gmail-api-push@system.gserviceaccount.com`, підписка (push на HTTPS-ендпоінт або pull).
- ⚠️ Вартість Pub/Sub і квоти Gmail API — перевірити за актуальними сторінками Google Cloud. Обсяг подій для MVP малий, але цифр без перевірки не наводжу.
- Простіша альтернатива для PoC: лише polling `history.list` раз на 1–2 хв без Pub/Sub. Затримка більша, GCP-конфігурація менша.

## 4. Telegram

- ✅ Бот не може написати першим: користувач має сам відкрити бота й натиснути Start. Тому підключення = посилання на бота з одноразовим токеном (`t.me/<bot>?start=<token>`), бекенд зіставляє токен з акаунтом і зберігає `chat_id`. ⚠️ Перевірити на практиці.
- ✅ Безкоштовно. Ліміти: ~1 повідомлення/с в один чат, ~30/с загалом для бота. Понад це — помилки 429 (потрібна черга і повтори з паузою). Платні розсилки до 1000/с коштують 0,1 Stars за повідомлення понад безкоштовні 30/с.
- ✅ Користувач може заблокувати бота — потрібно обробляти помилку доставки й показувати статус «канал недоступний».

## 5. Ризики

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Restricted-верифікація і CASA | Затримка публічного запуску на тижні, річні витрати | Почати зі статусу Testing, подати на верифікацію рано; розглянути альтернативу нижче |
| Watch не поновлено | Користувач мовчки перестає отримувати сповіщення | Щоденний cron поновлення + резервний `history.list` + статус у UI |
| Токен відкликано або прострочено | Скринька «відпала» | Показувати статус «потрібне повторне підключення», сповістити в Telegram |
| Дублі або пропуски | Довіра до продукту | `historyId` + таблиця оброблених листів, ідемпотентна відправка |
| Тема й відправник виходять у Telegram | Приватність: чати з ботами не мають наскрізного шифрування (⚠️ підтвердити) | Прозорі тексти в політиці приватності; опція «без теми, лише відправник» |
| Зберігання refresh token | Витік = доступ до пошти | Шифрування, секрети лише на сервері, RLS, відкликання при від'єднанні |

## 6. Альтернатива без restricted-scope (до обговорення)

Користувач сам налаштовує в Gmail пересилання на нашу адресу, а сервіс обробляє вхідні листи. Плюси: немає Google OAuth і CASA. Мінуси: через нас проходить повний вміст листів (суперечить принципу «лише метадані»), складніша настройка для користувача, зміна приватності й GDPR-оцінки. ⚠️ Не досліджено детально, лише як варіант.

## 7. Мінімальний тест PoC (потрібні твої акаунти)

1. GCP-проєкт, Gmail API, OAuth consent screen у статусі Testing, свій акаунт як тестовий користувач.
2. Telegram-бот через BotFather, токен лише в `.env`.
3. Node-скрипт: OAuth → `users.watch` (або polling) → `history.list` → `sendMessage`.
